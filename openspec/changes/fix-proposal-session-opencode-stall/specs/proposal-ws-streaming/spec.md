## MODIFIED Requirements

### Requirement: proposal-ws-client-message-id

The `ProposalWsClientMessage::Prompt` variant SHALL accept an optional `client_message_id` string field. When present, the server SHALL include this value in the corresponding `UserMessage` response. The field SHALL use `#[serde(default)]` for backward compatibility with clients that do not send it. Concurrent ACP requests generated by prompt, cancel, or elicitation flows MUST correlate responses by request ID so one request cannot consume another request's response.

#### Scenario: prompt-with-client-message-id

**Given**: A WebSocket client sends a Prompt message with `client_message_id: "user-123"`
**When**: The server processes the prompt
**Then**: The `user_message` response includes `client_message_id: "user-123"`

#### Scenario: prompt-without-client-message-id

**Given**: A WebSocket client sends a Prompt message without a `client_message_id` field
**When**: The server processes the prompt
**Then**: The `user_message` response does not include a `client_message_id` field and processing continues normally

#### Scenario: concurrent-acp-requests-do-not-drop-responses

**Given**: A proposal session backend sends multiple ACP requests whose responses may arrive out of order
**When**: the ACP subprocess returns those responses
**Then**: each response is delivered to the waiter registered for its request ID
**And**: the backend does not drop a response merely because another request is currently waiting

### Requirement: proposal-ws-server-message-types

The `ProposalWsServerMessage` enum includes `agent_thought_chunk` as a valid message type in addition to the existing types. The backend MUST classify ACP stdout messages by JSON-RPC shape so notifications, responses, and unsupported server requests are handled observably.

#### Scenario: frontend receives thought chunk

**Given**: A dashboard WebSocket client connected to a proposal session
**When**: A message with `type: "agent_thought_chunk"` is received
**Then**: The `onThoughtChunk` callback is invoked with the text content

#### Scenario: unsupported-server-request-is-observable

**Given**: The ACP stdout stream emits a JSON-RPC object containing both `method` and `id`
**When**: the backend parser processes the line
**Then**: the line is treated as an unsupported server request rather than a normal notification
**And**: a warning log is emitted so the protocol mismatch is visible

#### Scenario: non-u64-response-id-is-observable

**Given**: The ACP stdout stream emits a JSON-RPC response whose `id` is not a `u64`
**When**: the backend parser processes the line
**Then**: the backend does not silently match it to a pending request
**And**: a warning log is emitted describing the non-`u64` id
