- Both new regressions were confirmed to fail with the two cancellation-exit calls removed (`registered_execution_count()` stayed 1; `Stopped` was emitted while the merge was pending) and to pass with them present, so they are genuine regressions rather than tautologies.
- The new parallel regressions run on real Tokio time rather than `start_paused`: the real scheduler loop shells out to git during `prepare_for_parallel`, and paused-time auto-advance fires the test timers instead of waiting for those child processes. Because real time makes the scheduler's own progress uncontrollable, neither test orders itself against the loop with a fixed sleep: the only fixed wait is the 150 ms window in which terminal stop must *not* appear, and every other wait is event-driven, returning as soon as the awaited event arrives. Their `EVENT_WAIT` bound is a generous 5 s must-arrive timeout that is only ever reached once the assertion has already failed, so it costs nothing on the passing path.
- Ordering hand-off in `idle_parallel_stop_cancelled_scheduler_handles_pending_merge_before_stopped`: the injected `MergeResult` is sent only after the test has observed the drain's operator-visible `Waiting for 1 pending background merge/base-lane task(s)` log. That notice is emitted from inside `drain_pending_merge_results_after_cancellation`, i.e. after the loop has already left `wait_for_scheduler_event`, so its ordinary `merge_result_rx.recv()` select arm is unreachable and the drain's own recv loop is necessarily the receiver. The previous fixed-timer send left the two racing, and under full-suite load the select arm could consume the result before the loop observed cancellation, driving `pending_merge_count` to 0 and making the drain early-return without ever emitting the asserted log.
