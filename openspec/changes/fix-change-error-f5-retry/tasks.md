## Notes

- Start admission now lives in `RunControlService::classify_start_admission` (`src/orchestration/run_control.rs`), which owns the mode guard, the complete-request worktree fence, ordinary/retry class selection, and every target-specific exclusion. `prepare_start` and the composed `start` shorthand both route through it, so the coordinator-driven and unordered forms cannot diverge.
- `ExcludedTarget` gained a `detail` field and one `describe()` spelling, used by `describe_exclusions`, the TUI settlement wording, and the `/api/v2` summary, so both frontends report an exclusion identically.
- `AppState::admit_run_targets` no longer applies the run-scoped presentation reset when the process is already Running: a retry admitted into a live run must not clear the current change or restart the run's elapsed timer for unrelated work. Covered by `change_error_f5_retry_running_retry_preserves_the_live_run_presentation`.
- Running-mode Start is no longer an `InvalidMode` refusal; it is a target refusal when nothing marked is retryable. `accepted_operator_command_transaction_invalid_mode_has_no_effect` and the cross-adapter Start row were updated to that contract, with a dedicated no-effect test for the Running case. `start_is_refused_while_a_run_owns_the_lifecycle` now asserts the two refusal shapes separately, and `run_mark_intent_start_admission_rejects_when_no_runnable_target_remains` arranges its `error` row with active Apply-ceiling evidence, because a bare terminal error is routable now.
- Out of scope but repaired here: `promoted_duplicate_queue_state_synchronization_carries_the_new_contract` was already failing on this branch. `restore-running-mark-reanalysis` reworded the canonical `Queue State Synchronization` requirement to "MUST NOT *directly* modify DynamicQueue" without updating `simplify-tui-run-marks`'s promotion guard, which still asserted the replaced sentence. The guard now tracks the narrowed wording; its intent — Space carries no queue authority — is unchanged.
