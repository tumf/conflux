- evidence: `cargo test --lib` — 4491 passed, 0 failed, 18 ignored (pre-existing). 53 of those tests are this change's: `config::types::judge_commands_config_tests` (9), `judge_command::{cleanup_sequence,failure_category,response_parser,operator_documentation,judge_process}_tests` (27), `analyzer::tests::shadow_judge_{request,runtime}` (16), `parallel_run_service::tests::judge_outcomes_never_change_analysis_provenance` (1).
- evidence: `cargo clippy --all-targets -- -D warnings` passes; `cargo fmt --check` reports no diff.
- verification-type split for the judge runner (task 2): the cleanup *ordering* decisions (TERM → one fixed 100 ms grace → KILL only after it expires → always reap, and "elapsed time never proves a reap") are verified as true unit tests against an in-memory `JudgeProcessControl` double with no process, signal, or wall-clock dependency (`judge_command::cleanup_sequence_tests`), as is exit-code classification and the category token surface. The causal fake-executable tests named by the task (`judge_command::judge_process_tests`) additionally exercise the real process boundary — spawn failure, exact stdin delivery, bounded drains, oversize output, timeout, cancellation, TERM-ignoring escalation, and reaping — and are integration-scoped evidence by the unit-test boundary policy. Both run under the declared `cargo test --lib` command, so `shadow-dependency-judge-tests` is satisfied by evidence of each kind rather than by process tests labelled as unit.
- The analyzer runtime tests make judge/analyzer ordering *causal* rather than timing-based: the fake judge publishes a marker file and the conventional analyze command waits for it (or vice versa for the cancellation cases), so "the judge completed first" and "the judge was still running" are both deterministic. The slow-judge cases configure a 5-minute judge timeout, so a caller that waited for the judge would block instead of passing; each case is additionally wrapped in a generous `tokio::time::timeout` hang safeguard rather than asserting on elapsed time.
- Compatibility fixtures live in `tests/fixtures/judge_command/` with a README pinning `jev-cli v0.4.1` tag commit `50488f35d705051b5d621d1d10e69d1503783e7d` and stating that repository `main` is not a baseline. `src/judge_command.rs` consumes the response/request/error fixtures via `include_str!`; `docs/guides/CONFIG.md` is read at test time through `CARGO_MANIFEST_DIR` instead of being embedded, so the published crate does not have to carry `docs/`.
- In-flight nodes carry the ID the scheduler supplied plus their complete `proposal.md`, and deliberately no re-derived metadata (`metadata_dependencies: []`, `priority: null`, `references: []`), matching the design's request example. Their authoritative metadata is unaffected either way, since the judge never contributes a dependency.
- `JudgeFailureCategory` adds `invalid_request`, `authentication`, and `transient` alongside the design's named categories, which is where baseline exit codes 2, 3, and 4 are mapped. All of them remain non-authoritative shadow failures.
