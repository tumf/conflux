# Verification declaration integrity design

Every choice below was fixed against the integrated source at `ebfeecf7` (`fd0d2713` fail-closed plus `fix-rerun-leading-env`). Where a current type or route is named, the implementer reuses it; no new policy switch, hold category, store, or retry rule is introduced.

## Current boundaries being closed

- `parse_proposal_metadata_from_file` (`src/openspec.rs`) returns `ProposalMetadata` by value: a frontmatter decode failure becomes `verifications: Vec::new()`. Both `verify.rs::declarations` and `manifest_builder::build_manifest_for_workspace` use it, and the latter also substitutes an empty list when `proposal.md` is not a file. `split_frontmatter` returns the whole content as prose when the opening `---` has no closing delimiter.
- `validation.rs::validate_verification_declarations` inserts the *untrimmed* `id` into its duplicate set and then drops every planner `declaration_duplicate_id` as "reported above", so `valid-gate` / `" valid-gate "` passes strict and archive-gate while the planner (trimmed) rejects it.
- The executor's `GateVerdict::DeclarationInvalid` arm (`src/parallel/executor.rs`) formats one string per defect and wraps them with `crate::acceptance::legacy_findings`, so `normalize_findings` falls into `normalize_legacy_texts` and every declaration defect shares the identity `repository|code|[declaration_invalid]`. `FindingRepairLedger::observe_fail` therefore returns `Stop` for a newly exposed defect once any declaration defect consumed its repair.

## Source ownership

Add one fallible verification-source reader to `src/openspec.rs`, used by every execution-authoritative consumer:

- `parse_verification_source(content: &str, path: &Path) -> VerificationSource` works on already-read content (strict validation has the content). `read_verification_source(path) -> Result<VerificationSource, VerificationSourceUnavailable>` wraps it with the file read.
- `VerificationSource { declarations: Vec<VerificationDeclaration>, defects: Vec<VerificationSourceDefect> }`. `declarations` is empty whenever `defects` is non-empty, so a consumer that forgets to look at the defects still cannot plan a partially decoded list.
- `VerificationSourceDefect { key: DeclarationKey, position: usize, field: String, detail: String }`, with `position: 0` for proposal scope and the 1-based occurrence position otherwise.
- `pub enum DeclarationKey { Proposal, Position(usize /* 1-based */), Id(String /* trimmed, as authored */) }`, defined in `src/openspec.rs` next to `VerificationDeclaration` (the acceptance module already imports from there), deriving `Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize` with `#[serde(tag = "kind", content = "value", rename_all = "snake_case")]`, so it serializes as `{"kind":"proposal"}`, `{"kind":"position","value":3}`, or `{"kind":"id","value":"gate"}`. The `label() -> String` helper returns `<proposal>`, `<position N>`, or the trimmed ID (the planner's existing display label). Occurrence position is carried separately: source defects store `position: usize`, and `DeclarationDefect::new` takes that position explicitly. `Id(String)` intentionally carries no occurrence position, because a named identity must survive reorder; no `position()` helper can recover an occurrence index from this variant. `Id` holds whatever the trimmed string is, including one that is unstorable or literally spelled `<position 3>` or `<proposal>`: the key is provenance (did the author write an `id`), never a judgement about the ID. This one type is the declaration key for the reader, the planner, `DeclarationDefect`, and `NativeDeclarationIdentity`; no second encoding of "named / nameless / proposal-wide" exists anywhere on the path.
- `VerificationSourceUnavailable { path: PathBuf, kind: std::io::ErrorKind }`. A missing file (`NotFound`) and an unreadable file are the same typed value; the detail is the proposal path relative to the workspace plus the `ErrorKind` name, never file content.

Detection walks the `serde_yaml::Value` tree the strict parser already builds. The serde error `Display` text is never published, because serde messages can embed values (`invalid value: string "..."`, unknown-variant text). Rules, in order, each stopping further verification parsing:

1. Content starts with `---\n` and has no `\n---\n` closing delimiter: `Proposal` / `frontmatter` / "opened frontmatter block has no closing delimiter".
2. `serde_yaml::from_str` fails: `Proposal` / `frontmatter` / "frontmatter is not well-formed YAML at line L column C" using `Error::location()` only.
3. Root is neither a mapping nor null: `Proposal` / `frontmatter` / "frontmatter root is a <yaml type>, expected a mapping". A null root (empty block) is legitimately empty.
4. `verifications` present and neither a sequence nor null: `Proposal` / `verifications` / "verifications is a <yaml type>, expected a sequence". A null value (bare `verifications:` key) stays legitimately empty, which is what `Option<Vec<_>>` already decodes today and what strict validation already accepts for non-implementation proposals; rejecting it would fail existing valid proposals, not close a hole.
5. Per entry at 1-based position N: a non-mapping entry is `Position(N)` / `verifications` / "declaration at position N is a <yaml type>, expected a mapping". For a mapping entry the key is `Id(trimmed)` when its `id` is a string with non-empty trim, otherwise `Position(N)`; an unknown key is `<key>` / "unknown verification field"; a known string-valued field (`id`, `requirement`, `phase`, `owner`, `trigger`, `automation`, `evidence`, `rerun`, `execution_class`, `completion_role`) that is neither a string nor null is `<field>` / "<field> is a <yaml type>, expected a string"; `prerequisites` that is neither a sequence of strings nor null is `prerequisites` / "prerequisites is a <yaml type>, expected a sequence of strings". Every entry is checked, so one verdict lists every entry defect.

The yaml type vocabulary is fixed: `null`, `boolean`, `number`, `string`, `sequence`, `mapping`, `tagged`. The reader decodes `verifications` from the tree independently of the other top-level fields, so a wrong-typed `dependencies` or `priority` neither hides nor fabricates a verification defect; those fields keep their existing strict-validation diagnostics. Unknown top-level keys remain warnings. The display APIs (`parse_proposal_metadata_from_file`, `parse_proposal_frontmatter_strict`, `parse_proposal_dependencies_strict_from_file`) are unchanged for their existing callers.

## Shared plan entry

`DeclarationDefect` (`src/orchestration/acceptance/verification_evidence.rs`) gains one field, `pub key: DeclarationKey`, placed first, and one constructor, `DeclarationDefect::new(key: DeclarationKey, position: usize, field: &str, code: &str, detail: String)`, which fills `verification_id` from `key.label()` and keeps the explicit occurrence `position` (`0` for `Proposal`, otherwise 1-based; independent of named identity). The constructor is the only production construction path: the planner closure in `plan_declared_gates` (today `execution_manifest.rs:1448-1456`, which currently collapses `Option<trimmed id>` into a string label before building the struct) is changed to build `id.map(DeclarationKey::Id).unwrap_or(DeclarationKey::Position(position))` first and derive the label from it, so provenance is fixed at the one point where the source still knows whether an `id` was authored. `verification_id` and `position` stay as display projections for `summary()`, the text output, and the existing JSON fields. Existing test-only literal constructions (`execution_manifest/tests.rs`, `gate_execution/tests.rs`) add the field. The struct keeps its `Serialize, Deserialize` derives; `key` has no `#[serde(default)]`, because a defaulted key would be a second lossy reconstruction, and no production path deserializes `DeclarationDefect` (only `to_json` projections exist; verified by grep for `from_str`/`from_value`/`from_slice` over the manifest types at `ebfeecf7`).

`execution_manifest.rs` gains `plan_verification_source(&VerificationSource) -> DeclarationPlan`. With any source defect it returns zero gates and one `DeclarationDefect::new(defect.key.clone(), defect.position, &defect.field, "declaration_metadata_invalid", defect.detail.clone())` per source defect, in reader order; planner rules are not evaluated. Otherwise it is exactly `plan_declared_gates(&source.declarations)`. `summary()` is unchanged. `to_json()` keeps the five existing fields byte-identical and adds one additive `"key"` member holding the serde form above, so `declaration_defects` in verify JSON and in the manifest projection remain readable by every current consumer while a machine reader can distinguish a user ID spelled `<position 3>` from a nameless third entry; `position: 0` and `key` are the only new values.

## Consumer routing, exact outcomes

| Source state | `cflx openspec verify --plan` / run | strict / archive-gate validation | native Acceptance boundary |
| --- | --- | --- | --- |
| Readable, no frontmatter, no `verifications`, `verifications: []`, or `verifications:` null | unchanged: plan/run over zero required gates, exit 0 | unchanged change-type rules | unchanged: empty manifest, `GateVerdict::Proceed`, reviewer runs |
| Readable, structural defect | `report_declaration_defects` + `EXIT_UNSATISFIED`, before `resolve_store`; `--verification-id` does not narrow | error line per defect | manifest `declaration_defects` non-empty, `is_declaration_invalid()` true, existing `DeclarationInvalid` routes in `gate_execution.rs` and the executor `Fail` arm |
| Missing or unreadable `proposal.md` | the existing `Err(String)` route of `verify_in_workspace`, which already carries "no proposal at ... and no archived proposal", with its existing non-zero status, before `resolve_store` | unchanged (validation already fails a change without a readable proposal) | new `ManifestBuildError::ProposalUnreadable { path, kind }` returned by `build_manifest_for_workspace`; the executor's existing `Err(error)` arm turns it into `AcceptanceExecutionHold { category: ManifestMalformed, fingerprint: all-zero, evidence: [error.detail()] }` exactly as `Unobservable` is today |

`build_manifest` takes `&VerificationSource` instead of `&[VerificationDeclaration]` and calls `plan_verification_source`; `build_manifest_for_workspace` calls `read_verification_source` and maps the error. The hold is the chosen outcome because the current code already classifies "no manifest could be derived" that way and the admission guard in `execution_manifest.rs` (`Err(_) => AcceptanceAdmission::Admit`) already admits the next attempt without a repository change; no new `AcceptanceHoldCategory` is added. `ManifestMalformed::detail()` keeps its wording; the evidence line is what names the proposal path and `ErrorKind`. This is a refusal, never `Proceed`, never a `Fail` verdict, never `tool_unavailable`, and never an external-prerequisite block.

Validation parity: `validate_verification_declarations` calls `parse_verification_source` on the content it already has. When the reader reports defects, each is pushed as `"{change_id}: {defect.summary()}"` through the same `DeclarationDefect` projection and the raw `Failed to decode proposal frontmatter fields: ...` diagnostic is not pushed for that proposal (it would duplicate the defect and may echo values); when the reader reports none, the existing diagnostics for the other top-level fields are kept as today. The validator's own untrimmed duplicate loop is removed and `declaration_duplicate_id` leaves the `REPORTED_ABOVE` suppression list, so every duplicate occurrence is reported once by the planner with its trimmed ID and positions. The other three suppressed codes stay suppressed because the per-field checks above them do report those conditions with the verification and field named. An all-whitespace `id` is already reported as `missing non-empty id` and is treated as missing by the planner, so it collides with nothing.

## Typed identity

`src/acceptance.rs`: `AcceptanceFinding` gains a third private field `native: Option<NativeDeclarationIdentity>` next to `structured`, with `pub struct NativeDeclarationIdentity { change_id: String, key: DeclarationKey, field: String, code: String }` and `pub fn comparison_identity(&self) -> String`. The encoding is `"repository|declaration|"` followed by the `serde_json` string of the five-element array `[change_id, key_tag, key_value, field, code]` where `key_tag` is `"id"`, `"position"`, or `"proposal"` and `key_value` is the trimmed ID, the decimal position, or `""`. The tag comes from the typed `DeclarationKey` variant, never from the label text, so `Id("<position 3>")` encodes as `["c","id","<position 3>",...]` and a nameless third entry as `["c","position","3",...]`; JSON escaping additionally keeps an ID containing `|`, `"`, or `,` unambiguous.

Constructor: `AcceptanceFinding::declaration_defect(text: String, identity: NativeDeclarationIdentity)`. `NativeDeclarationIdentity::from_defect(change_id: &str, defect: &DeclarationDefect)` copies `defect.key.clone()`, `defect.field`, and `defect.code`; it does not read `verification_id` or `position` and performs no string comparison, prefix parse, or `position == 0` inference, because the key was fixed by the reader or planner while the source still knew whether an `id` had been authored. There is no other constructor from a label. The executor's `DeclarationInvalid` arm builds the same human text it builds today (`[DECLARATION_INVALID] <proposal path>: <summary> — ...`, candidate short hash included as prose) and constructs one such finding per defect instead of calling `legacy_findings`. The `GateVerdict::Failed` arm and every reviewer path are untouched.

Consequences the regressions must pin: a declaration whose authored `id` is literally `<position 3>` (or `<proposal>`) sitting at position 3 with a `rerun` shell-syntax defect is keyed `Id("<position 3>")` and does not share an identity with a nameless entry at position 3 carrying the same field and code; moving that declaration to position 1 leaves its identity unchanged; a nameless entry is keyed by its position and a proposal-wide defect by `Proposal`; an unstorable authored ID (for example `../x`, code `declaration_unstorable_id`) is keyed `Id("../x")` so the diagnostic and the ledger still name the ID the author wrote; the verify JSON `key` member carries the same variant; and reviewer-authored `RepositoryFinding` identities and coverage are byte-identical before and after.

`normalize_findings` checks `native` first, then `structured`, then the legacy text fallback, so no prose parsing is added and `normalize_legacy_texts` is unchanged. `declares_paths()` remains `structured.is_some()`: a native finding never acquires reviewer remediation-coverage obligations. `repository_findings` treats a native finding as repository-scoped. `id()` keeps its reviewer-ID meaning and returns `None` for native findings. `to_json()` adds a `declaration_identity` object (`change_id`, `key`, `field`, `code`) for native findings as observability only. Because `AcceptanceAttempt.findings`, `AcceptanceResult::Fail { findings }`, and `AcceptanceRepairStop.findings` all hold `AcceptanceFinding` values, the identity travels by the same clone with no extra plumbing; nothing is persisted, and after an owner restart it is recomputed from the candidate's `proposal.md`.

`FindingRepairLedger` is unchanged. Two `declaration_duplicate_id` occurrences of one ID share `(Id, "id", declaration_duplicate_id)` and are deduplicated to one ledger identity by the existing `dedup_by`, while both complete findings stay in the recorded attempt and the `Fail` payload. The later `(Id, "rerun", declaration_shell_syntax)` is a different identity and receives its first repair; the same identity observed again after `record_repair_dispatched` still returns `Stop`. List order, line numbers, candidate OID, and detail wording are not identity inputs.

## Alternatives rejected

- Relying on strict base validation: Apply changes candidate metadata, so it does not certify the later reader.
- Rejecting every empty list or a null `verifications` value: valid legacy/spec-only/non-required proposals are intentionally zero-gate, and today's strict validation already accepts them.
- A `Fail` verdict or a new hold category for an unreadable proposal: the existing manifest-build error route already states the exact outcome and admits the next attempt; adding a category would be new policy with no consumer.
- Config flag or manual candidate repair: bypasses the product contract and the user's requested fix.
- Parsing a longer prose prefix or resetting repair budgets: loses typed ownership or weakens repeated-finding protection.
- Forcing full reviewer structured findings on native declaration defects: introduces unrelated remediation coverage obligations; native identity stays orthogonal.
- Publishing serde error text: it can embed values, and the type/location vocabulary carries everything a repair needs.

## Compatibility

The leading-env command type and shared planner remain authoritative; preserve env redaction and no implicit shell. No API/UI addition is required; the only serialized additions are `position: 0` and the additive `key` member in existing `declaration_defects` projections and the observability-only `declaration_identity` on native finding JSON. No existing JSON field is renamed, retyped, or removed. If provenance or candidate refresh integrates first, consume its current interfaces without rewriting those features or depending on their runtime artifacts. No existing managed worktree is edited during proposal preparation.
